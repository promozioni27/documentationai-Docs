## Release Note Patterns

<Tabs>
  <Tab title="Short release note" icon="zap">

Use this format when you need a concise entry:

```markdown
### Improvements

- Reduced the number of clicks needed to reach the latest record.
- Updated the page layout for faster scanning.
```

  </Tab>
  <Tab title="Detailed release note" icon="book-open">

Use this format when you need more context for the change:

```markdown
### Behavior Changes

- Search now returns results in a more stable order.
- Export actions now complete asynchronously so large files do not block the interface.
```

  </Tab>
  <Tab title="Team-friendly note" icon="users">

Use this format when multiple teams contribute to the same release:

```markdown
### Bug Fixes

- Fixed a validation issue in saved filters.
- Corrected a label mismatch in the settings panel.
- Improved error handling for failed requests.
```

  </Tab>
</Tabs>

## Best Practices

- Keep each entry focused on what changed, not on internal implementation details.
- Write for readers who need to understand impact, not just the release process.
- Use action-oriented language so you explain what you changed and what users should do next.
- Avoid overloading one entry with too many unrelated updates.

<Callout kind="info">
  If you document regulated or user-facing behavior, include enough context for support, operations, and end users to understand the impact.
</Callout>
